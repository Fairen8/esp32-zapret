# Статистика: формат отчётов и требования к бэкенду

Документ для агента, который пишет сайт и бэкенд `statistics.fairen8.ru`.
Описывает всё поведение прошивки esp32-zapret (начиная с v1.0.1) и контракт,
которому обязан соответствовать сервер.

## 1. Что происходит на устройстве

- Отправка **включена по умолчанию** (начиная с v1.1.1). Выключается командой
  `/stats off` (флаг в NVS), тумблером в веб-UI или сборкой с
  `CONFIG_APP_STATS_DEFAULT_ON=n`.
- Отчёт — анонимный: в payload **нет** идентификаторов (ни ID устройства или
  чата, ни SSID, ни IP-адресов, ни токенов).
- Устройство не показывает пользователю ошибки отправки: любая неудача молча
  игнорируется (в лог уровня debug).
- Устройство не отправляет время: сервер обязан сам ставить timestamp
  получения. В payload есть только `uptime_s` (секунды с загрузки).

## 2. Транспорт (жёсткие требования)

| Параметр | Значение |
|---|---|
| Метод и URL | `POST https://<host>/api/v1/report` |
| Host | `statistics.fairen8.ru` (Kconfig `APP_STATS_HOST`) |
| Протокол | HTTP/1.1, `Connection: close` |
| `Content-Type` | `application/json` |
| `User-Agent` | `esp32-zapret/<версия>`, напр. `esp32-zapret/1.0.1` |
| `Accept` | `application/json` |
| Размер тела | ~300–400 байт (буфер устройства 512 байт) |
| Таймаут ответа | 8 секунд; TLS-handshake — 6 с; TCP — 2,5 с на адрес |

Обязательно:

- **A-запись IPv4.** Устройство резолвит только A (и через DoH тоже A);
  IPv6/AAAA не используется. Если у домена только AAAA — не заработает.
- **Валидный TLS-сертификат для имени `statistics.fairen8.ru`** (Let's Encrypt
  подходит). Проверка сертификата обязательна (`esp_crt_bundle`), SNI =
  hostname. Сервер должен принимать **TLS 1.2** и стандартные ECDHE
  AES-GCM/CHACHA-шифры.
- **Никаких редиректов.** 3xx устройство не обрабатывает (`Location` не
  читается) — считает это ошибкой. Ответ должен быть 2xx сразу.
- **Успех = любой HTTP 2xx.** Тело ответа не парсится и не важно: можно
  `204 No Content` или `200 {}`.
- Авторизация/cookies не нужны и не должны требоваться (прошивка не хранит
  секретов). Не запрашивайте API-ключи.
- HTTP (порт 80) может отвечать 403/400 — это не важно, устройство ходит
  только по HTTPS.

Если сервер ответит 4xx/5xx, таймаут (>8 c) или оборвёт соединение — отчёт
считается недоставленным, устройство молча повторит его в следующий период.

## 3. Формат отчёта (schema = 1)

Плоский JSON-объект. Все поля присутствуют всегда. Порядок полей не важен, но
устройство шлёт их именно так:

```json
{"schema":1,"event":"boot","fw":"1.0.1","target":"esp32","uptime_s":47,
 "heap":214512,"rssi":-63,"reset":1,"mode":4,"fool":1,"ttl":5,
 "split1":-1,"split2":-1,"have":true,
 "strategy":"fake_split fool=ttl ttl=5 sni=www.iana.org",
 "scans":1,"probes":2,"fails":1}
```

### Поля

| Поле | Тип | Значение |
|---|---|---|
| `schema` | int | Версия схемы. Сейчас всегда `1`. При несовместимом изменении — инкремент. |
| `event` | string | `"boot"` — первый отчёт после загрузки; `"periodic"` — ежедневный; `"manual"` — сразу после `/stats on`. |
| `fw` | string | Версия прошивки, из файла `VERSION` (например `"1.0.1"`). |
| `target` | string | Чип: `"esp32"`, `"esp32s3"`, `"esp32c3"`. |
| `uptime_s` | uint32 | Секунды с момента загрузки. |
| `heap` | uint32 | Свободная heap, байт. |
| `rssi` | int | Уровень Wi-Fi, dBm, обычно −30…−90. `0`, если информация недоступна. |
| `reset` | uint8 | Причина перезагрузки (см. таблицу ниже). |
| `mode` | uint8 | Режим обхода (см. таблицу ниже). Отражает конфиг на момент отправки. |
| `fool` | uint32 | Битмаска фулинга (см. таблицу ниже). |
| `ttl` | uint8 | TTL фейкового пакета, 1–255. Для режимов без fake обычно `64`. |
| `split1` | int16 | Позиция первого сплита, `-1` = автоматически. |
| `split2` | int16 | Позиция второго сплита, `-1` = автоматически (середина SNI). |
| `have` | bool | Найдена ли рабочая стратегия (`true`/`false`). |
| `strategy` | string | Человекочитаемое описание стратегии, ≤80 символов; `""` если `have=false`. Примеры: `"off"`, `"split"`, `"fake_split fool=ttl ttl=5 sni=www.iana.org"`, `"fake fool=md5sig ttl=64 sni=www.iana.org"`. |
| `scans` | uint32 | Переборов стратегий с момента загрузки. |
| `probes` | uint32 | Всего проб TLS с момента загрузки. |
| `fails` | uint32 | Неудачных проб с момента загрузки. |

### `mode`

| Значение | Режим |
|---|---|
| 0 | `off` (обход выключен) |
| 1 | `split` |
| 2 | `disorder` |
| 3 | `fake` |
| 4 | `fake_split` |
| 5 | `tlsrec` |
| 6 | `seqovl` |

### `fool` (битмаска, возможны комбинации)

| Бит | Значение |
|---|---|
| 0 | `none` |
| 1 (`1<<0`) | `ttl` |
| 2 (`1<<1`) | `badsum` |
| 4 (`1<<2`) | `badseq` |
| 8 (`1<<3`) | `md5sig` |
| 16 (`1<<4`) | `datanoack` |
| 32 (`1<<5`) | `ts` |

Например, `fool=9` = `ttl|md5sig`.

### `reset`

Стандартные значения `esp_reset_reason_t` (ESP-IDF):

| Значение | Причина |
|---|---|
| 0 | unknown |
| 1 | poweron |
| 2 | ext (не применимо к ESP32) |
| 3 | sw (esp_restart) |
| 4 | panic |
| 5 | int_wdt |
| 6 | task_wdt |
| 7 | wdt |
| 8 | deepsleep |
| 9 | brownout |
| 10 | sdio |
| 11 | usb |
| 12 | jtag |
| 13 | efuse |
| 14 | pwr_glitch |
| 15 | cpu_lockup |

### Примеры

Есть рабочая стратегия, периодический отчёт:

```json
{"schema":1,"event":"periodic","fw":"1.0.1","target":"esp32c3","uptime_s":86430,
 "heap":201388,"rssi":-71,"reset":3,"mode":0,"fool":0,"ttl":64,
 "split1":-1,"split2":-1,"have":true,"strategy":"off","scans":1,"probes":1,"fails":0}
```

Стратегия не найдена (провайдер блокирует всё, что умеет прошивка):

```json
{"schema":1,"event":"periodic","fw":"1.0.1","target":"esp32s3","uptime_s":7205,
 "heap":199104,"rssi":-55,"reset":9,"mode":4,"fool":8,"ttl":64,
 "split1":-1,"split2":-1,"have":false,"strategy":"","scans":3,"probes":42,"fails":42}
```

## 4. Каденция и семантика доставки

| Событие | Когда отправляется | Ограничение |
|---|---|---|
| `boot` | после загрузки, Wi-Fi + SNTP + авто-подбор стратегии | не чаще 1 раза в час с последней **успешной** отправки |
| `periodic` | из основного цикла | не чаще `APP_STATS_INTERVAL_S` (по умолчанию 86400 с; диапазон 3600…604800) с последней **успешной** отправки |
| `manual` | сразу после `/stats on` | без ограничений (пользователь попросил) |

- Метка последней успешной отправки хранится в NVS и обновляется **только при
  2xx**. Неудача → следующая попытка в следующий период (при загрузке — не
  раньше чем через час от последней успешной).
- Ретраев внутри одной попытки нет.
- Дедупликации на устройстве нет: если сервер принял отчёт, но ответ не
  дошёл, устройство повторит его позже. Дубликаты возможны и допустимы.
- Максимум от одного устройства: 1 отчёт/час (boot) + 1 отчёт/сутки
  (periodic), плюс редкие `manual`.

## 5. Обязанности бэкенда

1. Принимать `POST /api/v1/report`, валидировать JSON и типы полей.
   Неизвестные поля игнорировать (задел на развитие схемы). Битый JSON или
   неверные типы → `400` (тело любое).
2. Другие методы на этот путь → `405`.
3. Отвечать быстро (рекомендуется <1 с, максимум 8 с) и без редиректов.
4. Ставить серверный timestamp получения (UTC) — клиентского времени в
   payload нет.
5. **Не сохранять IP-адрес клиента** (обещание анонимности). Для анти-абьюза
   достаточно in-memory счётчиков; если сервер за прокси, не персистить
   `X-Forwarded-For`.
6. Хранить сырой JSON (например, `JSONB`) + разобранные поля — схема может
   расширяться, сырые данные не должны теряться.
7. Ограничения: тело ≤1 КБ (иное → `413`), простой rate limit на IP
   (рекомендуется ≤60 запросов/мин; при превышении — `429`, устройство молча
   пропустит). Референсная реализация (statistics.fairen8.ru): **20 запросов с
   ошибкой (400) с одного IP → `429` на 30 минут**; успешные 2xx в счётчик не
   попадают. Учтите, что IP у устройств мобильные/домашние и часто меняются.
8. Считать каждый отчёт событием; дедупликация не требуется и невозможна
   (идентификаторов нет).
9. HTTPS обязателен; на HTTP-порту допустимо отвечать `400`/`403`, но **не
   3xx-редиректом**.

## 6. Визуализация (рекомендации)

- Временные ряды: отчёты в день, по `event`, по `fw`, по `target`.
- Распределение стратегий: распарсить `strategy` (mode + fool + ttl + sni),
  топ-N; отдельно доля `have=false` (провайдер не поддался).
- Доля `mode=0` (`off`) — сети без фильтрации.
- Число `reset` с причинами `panic`/`brownout`/`wdt` — сигнал проблем с
  питанием или прошивкой.
- Гистограмма `rssi`, медиана `heap`, распределение `scans`/`probes`/`fails`.
- Полезен фильтр по дням и разбивка по `fw` (какие версии ещё в поле).

## 7. Приёмочные тесты

Тела с пробелами (а `strategy` всегда с пробелами) **нельзя** передавать
инлайн через `-d '{...}'` в cmd/PowerShell: кавычки калечат JSON, а серверный
«ремонт» битого JSON покрывает только простые тела — искалеченный полный
отчёт будет отклонён. Всегда пишите тело в файл и используйте `--data-binary`.

### Windows (cmd)

```bat
echo {"schema":1,"event":"manual","fw":"1.1.0"}>body.json
curl --tlsv1.2 --tls-max 1.2 --ssl-no-revoke -i -X POST https://statistics.fairen8.ru/api/v1/report -H "Content-Type: application/json" -H "User-Agent: esp32-zapret/1.1.0" --data-binary @body.json
```

### Windows (PowerShell)

```powershell
curl.exe --tlsv1.2 --tls-max 1.2 --ssl-no-revoke -i -X POST https://statistics.fairen8.ru/api/v1/report -H "Content-Type: application/json" -H "User-Agent: esp32-zapret/1.1.0" --data-binary "@body.json"
```

(`curl.exe` — именно внешний curl, а не алиас `Invoke-WebRequest`.)

### Linux/macOS

```bash
curl -i -X POST https://statistics.fairen8.ru/api/v1/report \
  -H 'Content-Type: application/json' --data-binary @body.json
```

### Проверки

1. Полный валидный отчёт (примеры в §3, сохранить в `body.json`) → `204` или
   любой 2xx.
2. Неизвестное поле в теле → всё равно 2xx (игнорируется).
3. Битый JSON (`{"broken`) → `400`.
4. Не POST (GET) → `405`.
5. `--tlsv1.2 --tls-max 1.2` — TLS 1.2 работает (в прошивке mbedTLS);
   `--ssl-no-revoke` — для curl на Windows.
6. Редиректов нет: ответ на POST — 2xx, не 301/302/308.
7. A-запись: `nslookup -type=A statistics.fairen8.ru` (Windows) /
   `dig +short A statistics.fairen8.ru`.

### Защита от «плохих» тестов

- 20 запросов с ошибкой (400) с одного IP → `429` на 30 минут. Успешные (204)
  в счётчик не попадают.
- Упёрлись в 429 — подождать 30 минут или тестировать с другого IP.

Критерий готовности: полный отчёт из `body.json` возвращает 2xx, попадает в
базу и виден на дашборде; битый JSON отклоняется с 400.
